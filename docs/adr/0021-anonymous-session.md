# ADR 0021 — Anonymous session: a signed cookie, required to write

- **Status:** accepted · **Origin:** SPEC 0084

## Context
The public demo has no login (user decision, 2026-11-24), but it has to be possible to say which browser did something, and to limit it. The name that goes with an attempt is typed by hand and proves nothing.

## Decision
- ASP.NET Core cookie authentication with an anonymous identity whose only claim is an id generated by the server. Not a mechanism of our own: if a login ever comes, it enters here.
- The web asks for it when it starts (`GET /api/session`). Creating it on the first request would give several to the simultaneous ones of the first load.
- Everything written under `/api` needs the session **and** a header of its own: two independent barriers against forged requests (`SameSite=Strict` is the other one). Reads stay open.
- The signing keys are in the database, read through a connection without retries. With those of the business context, a database still waking up held the start of the API for a minute.
- It is always required; only the Testing environment can turn it off, and any other one refuses to start.

## Consequences
- It identifies a browser, not a person: clearing the cookies starts another one. The limits per IP (0089) are the real ceiling.
- The keys are stored unencrypted in the database. Whoever reads them could forge sessions, but a session grants nothing beyond what any visitor can do.
- Scripts that write (the demo loader, the E2E) ask for a session first. The demo reset does not need one: it has its own key (ADR 0014).
